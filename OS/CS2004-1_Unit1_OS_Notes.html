PID 01

What an Operating System Does · OS Services

An operating system is the program that manages the computer's hardware, acting as an intermediary between users/applications and the machine. Two complementary views: resource allocator (decides who gets CPU time, memory, I/O — fairly and efficiently) and control program (supervises execution, prevents errors and improper use). The one program running at all times is the kernel; everything else is system programs or applications.

OS services — the exam list

🧑‍💻
Helpful to the user
VISIBLE SERVICES

User interface (CLI/GUI/touch) · Program execution (load, run, end normally or with error) · I/O operations (user programs can't drive devices directly) · File-system manipulation (create, delete, read, write, search, permissions) · Communications (between processes, same machine or networked — shared memory or message passing) · Error detection (CPU, memory, I/O, program errors — detect, and act to keep computing consistent).

⚙️
Ensuring efficient operation
SYSTEM-FACING SERVICES

Resource allocation (CPU cycles, memory, files, I/O among concurrent users/jobs) · Logging / accounting (which users use how much of what — billing, statistics, tuning) · Protection & security (control access to system resources; authenticate users; defend against outsiders). Protection = internal correctness; security = external defense.

PID 02

User–OS Interface · System Services

Three interface styles

  • Command-line interface (CLI / shell) — commands typed at a prompt; the shell (bash, PowerShell) either contains the command's code or (UNIX way) locates a system program of that name and runs it — so adding commands doesn't change the shell. Faster for experts, scriptable.
  • Graphical user interface (GUI) — desktop metaphor: windows, icons, menus, pointer. Discoverable, friendlier to non-specialists.
  • Touch-screen interface — gestures (tap, swipe, pinch) replace keyboard/mouse; standard on mobile OSes.
  • The choice is preference/context; many systems provide all (macOS: Aqua GUI + Terminal). System administrators and power users lean CLI; end users lean GUI/touch.

System services (system programs)

The layer between the OS proper and application programs — convenient environment for program development and execution:

  • File management — create, delete, copy, rename, print, list files/directories.
  • Status information — date, disk/memory usage, performance monitors, logging.
  • File modification — text editors, search, transformation tools.
  • Programming-language support — compilers, assemblers, debuggers, interpreters.
  • Program loading and execution — loaders (absolute, relocatable), linkage editors, debuggers (→ PID 04).
  • Communications — remote login, messaging, file transfer, browsers.
  • Background services (daemons) — launched at boot, run while the system runs: network daemons, schedulers, print servers.
PID 03

System Calls

System calls are the programming interface to the services the OS provides — the only doorway from user code into the kernel. Hardware enforces the boundary with a mode bit: user mode (1) for applications, kernel mode (0) for the OS; privileged instructions execute only in kernel mode. A system call executes a trap (software interrupt): mode switches to kernel, the kernel performs the service, then returns to user mode.

KERNEL MODE (mode bit = 0)

  • API vs system call: programmers use an API (C library, Win32, POSIX) — e.g. printf() calls the write() system call underneath. APIs give portability and convenience; the run-time environment (RTE) provides the system-call interface that traps into the kernel by number.
  • Parameter passing — three methods: (1) in registers (fastest, limited count); (2) in a memory block/table whose address is passed in a register (Linux for >5 params); (3) pushed on the stack by the program, popped by the OS.

PID 04

Linkers & Loaders

How does main.c become a process in memory? The pipeline:

source (main.c) ──compiler──▶ object file (main.o) relocatable machine code, unresolved symbols main.o + other .o + libraries ──LINKER──▶ executable (a.out / .exe) one file, symbols resolved executable ──LOADER──▶ process image in memory ready to run (./a.out makes the shell fork + exec, and exec invokes the loader)
  • Linker — combines relocatable object files into a single executable: resolves cross-file references (printf → its library code), arranges sections, performs relocation (adjusting addresses to final layout).
  • Loader — brings the executable into memory, sets up the process's address space, and starts it at the entry point; relocation may finish here for load-time-decided addresses.
  • Static linking — library code copied into the executable: self-contained but large, duplicated in every program.
  • Dynamic linking (DLLs / shared objects .so) — linking postponed to load/run time: the executable holds a stub; first call locates or loads the shared library, and all processes share one in-memory copy. Saves disk + memory, and library updates don't require relinking programs.
  • Executable formats: ELF (Linux) / PE (Windows) — headers describe sections (text, data), entry point, needed libraries.
MASTER CHECK · 04
  1. Draw the source→process pipeline labeling compiler, linker, loader, and what each resolves.
  2. Static vs dynamic linking — two advantages each.
  3. What exactly happens on ./a.out? shell fork()s; child exec()s; exec invokes the loader; ELF headers drive memory setup.
PID 05

Process Concept · States · PCB

A process is a program in execution — the unit of work of a modern system. A program is a passive file on disk; a process is active, with a program counter and a full memory image. One program can spawn several processes (run it twice = two processes, same text).

Memory layout of a process

  • Text — the executable code (fixed size).
  • Data — global variables (fixed size).
  • Heap — memory allocated dynamically at run time (malloc) — grows upward.
  • Stack — function-call frames: parameters, return addresses, locals — grows downward toward the heap; the OS must keep them from colliding.

Process states — the diagram that must be drawn from memory

the amber token lives one process lifetime: new → ready → running → waiting (I/O) → ready → running → terminated
  • new — being created · ready — waiting for a CPU · running — instructions executing (one per core!) · waiting/blocked — awaiting an event (I/O completion, signal) · terminated — finished, awaiting cleanup.
  • Key edges: ready→running only via the dispatcher; running→ready via interrupt/preemption; running→waiting is voluntary (the process asked for I/O); waiting→ready when the event fires — never waiting→running directly.

Process Control Block (PCB) — the process's identity card

What the kernel stores per process

Process state · Program counter (next instruction) · CPU registers (saved on interrupt) · CPU-scheduling info (priority, queue pointers) · Memory-management info (page tables/base-limit) · Accounting info (CPU used, time limits, PID) · I/O status (open files, allocated devices). The PCB is what gets saved/restored at every context switch — it is the process, as far as the kernel is concerned.

"Waiting" and "ready" both mean 'not running' but are opposite situations: ready lacks only a CPU; waiting cannot use a CPU even if offered one. Merging them in the diagram is the classic lost mark.

PID 06

Process Scheduling · Queues · Context Switch

  • Goal of multiprogramming: some process running at all times (CPU utilization); of time sharing: switch fast enough that every user can interact. The process scheduler selects who runs; the degree of multiprogramming = number of processes in memory.
  • Queues: the ready queue (PCBs of ready processes, typically a linked list) and per-device/event wait queues. A process migrates: ready → CPU → (I/O wait queue → ready) or (time slice expires → ready) or (create child, wait → ready) … until termination. This picture is the queueing diagram — drawable from the state diagram of PID 05.
  • Process behavior: I/O-bound (many short CPU bursts, lots of I/O) vs CPU-bound (few, long bursts). A good mix keeps both CPU and devices busy.
  • Schedulers (classical terminology): long-term — which jobs enter memory (controls degree of multiprogramming, runs rarely); short-term / CPU scheduler — which ready process gets the CPU next (runs every few milliseconds — must be fast); medium-term — swap processes out/in to reduce memory pressure.
  • Context switch: on an interrupt or system call the kernel saves the current process's context (into its PCB) and loads another's. Pure overhead — no useful work during the switch (typically a few μs); speed depends on hardware (register sets, memory speed).
Frequent 5-marker: queueing diagram + the three schedulers with frequency ("seconds/minutes · milliseconds · as-needed") + context-switch definition with the word overhead.
PID 07

Operations on Processes — Creation & Termination

Processes form a tree: a parent creates children via fork(), each with a unique PID. On UNIX:

pid_t pid = fork();
if (pid < 0) {…} // fail
else if (pid == 0) // CHILD
  execlp("/bin/ls","ls",NULL);
else { // PARENT
  wait(NULL);
  printf("child done");
}
PID 512 parent — calls fork()
PID 613 child — exact copy, fork() returned 0
child exec()s → address space replaced by /bin/ls
exit(status) → parent's wait() collects status
  • fork() — duplicates the caller: child gets a copy of the address space and continues after the fork. Return value distinguishes them: 0 in the child, child's PID in the parent — that's the whole trick of the if-ladder.
  • exec() family — replaces the process's memory image with a new program (same PID, new code). fork + exec = how the shell runs every command.
  • wait() — parent blocks until a child terminates; collects the exit status.
  • exit(status) — voluntary termination; OS deallocates resources. Parents can also kill children (needing the child's PID — one reason fork returns it).
  • Zombie — child terminated but parent hasn't wait()ed: only the PCB entry lingers, holding the status. Orphan — parent died first; init/systemd adopts the child and wait()s. Cascading termination — some systems kill all descendants when a parent dies.
P1 · How many processes does this create? fork(); fork(); fork(); Each fork doubles the population: 2 × 2 × 2 = 8 total → 1 original + 7 children. General rule: n consecutive forks ⇒ 2ⁿ processes (2ⁿ − 1 new). P2 · if(fork()==0) fork(); → original forks (2 processes); only the child forks again → 3 processes. Draw the tree; count nodes — never guess. P3 · What prints? x=5; if(fork()==0){x+=5;} else {x-=5;} → child prints 10, parent prints 0 — separate copies: fork copies the address space; they don't share x.

PID 08

Inter-Process Communication (IPC)

Independent processes neither affect nor are affected by others; cooperating processes share data — for information sharing, computation speedup (parallel subtasks), and modularity. Cooperation requires IPC, in two fundamental models:

🗄️
Shared Memory
FAST · APP-MANAGED

One process creates a shared region; others attach it to their address space; they read/write directly. Kernel involved only at setup → fastest IPC (memory speed). Burden: the processes themselves must synchronize access (Unit II's whole story). Canonical use: the producer–consumer bounded buffer — a circular array with in/out pointers; producer waits when full ((in+1)%SIZE == out), consumer waits when empty (in == out).

📨
Message Passing
SIMPLER · KERNEL-MEDIATED

Processes exchange via send(msg) / receive(msg) — no shared variables; every message crosses the kernel (slower, but easy across machines, and no user-level sync needed). Design axes: naming — direct (name the process: send(P,msg)) vs indirect (mailboxes/ports shared by many); synchronization — blocking (synchronous) vs non-blocking (asynchronous) send/receive (blocking send + blocking receive = rendezvous); buffering — zero capacity (sender must wait), bounded (wait when full), unbounded (never waits).

AspectShared memoryMessage passing
SpeedFastest (memory access)Slower (kernel per message)
Kernel roleSetup onlyEvery send/receive
SynchronizationProgrammer's problemProvided by the primitives
Best forLarge data, same machineSmall messages, distributed systems
The bounded-buffer with the "one slot wasted" full test — full when (in+1)%n == out, empty when in == out, hence at most n−1 items — is a favorite short question. Be able to write both loops.

PID 09

Threads · Multithreading Models

A thread is the basic unit of CPU utilization: its own thread ID, program counter, registers, and stack — while sharing with sibling threads of the same process the code, data, and OS resources (open files, signals). A word processor is the standard picture: one thread for keystrokes, one for spell-check, one for autosave — all in one address space.

  • Benefits: responsiveness (UI thread lives while workers block), resource sharing (no IPC needed — same memory by default), economy (creating/switching threads is far cheaper than processes), scalability (threads run in parallel across cores).
  • User threads — managed by a thread library (Pthreads, Java) above the kernel; kernel threads — managed by the OS. The mapping between them is the multithreading model:
🔻
Many-to-One
N USER → 1 KERNEL

Thread library does everything; efficient switching — but one blocking system call blocks all threads, and no parallelism on multicore (only one thread in the kernel at a time). Historic (early Java green threads).

↔️
One-to-One
1 USER → 1 KERNEL

Each user thread gets a kernel thread: true concurrency, one blocked thread doesn't stall the rest. Cost: kernel thread per thread → creation overhead limits thread count. Linux & Windows use this.

🔀
Many-to-Many
N USER → ≤N KERNEL

Multiplex many user threads over a smaller/equal pool of kernel threads: create threads freely and get parallelism; blocking handled by scheduling another user thread on the kernel thread. Variant: two-level — many-to-many plus the option to bind a user thread to a kernel thread.

"Threads share everything" is false — each thread owns its stack and registers. Shared: code, data (globals!), heap, open files. That globals are shared is exactly why Unit II's synchronization exists.

PID 10

CPU Scheduling — Basic Concepts & Criteria

  • Why: a process alternates CPU bursts and I/O bursts (the CPU–I/O burst cycle). While one process waits on I/O, the CPU would idle — so the OS gives it to another. Burst histograms: many short bursts, few long ones — the shape that motivates SJF and RR.
  • When decisions happen: (1) running→waiting (I/O request), (2) running→ready (interrupt), (3) waiting→ready (I/O completes), (4) termination. Scheduling only at 1&4 = non-preemptive/cooperative; otherwise preemptive (needs a timer; raises shared-data races → Unit II).
  • Dispatcher — the module that hands the CPU over: context switch, switch to user mode, jump to the program's location. Its cost = dispatch latency — pure overhead, keep it tiny.

Scheduling criteria — what "good" means

CriterionDefinitionGoal
CPU utilizationFraction of time the CPU does useful workMaximize
ThroughputProcesses completed per time unitMaximize
Turnaround time (TAT)Submission → completion: TAT = CT − ATMinimize
Waiting time (WT)Total time in the ready queue: WT = TAT − BTMinimize (the only part scheduling controls!)
Response timeSubmission → first response (interactive systems)Minimize / bound the variance
TAT = Completion − Arrival   ·   WT = TAT − Burst   ·   Response = first-CPU − Arrival These three lines solve every numerical in PID 11. Scheduling can't shorten bursts or I/O — only the queueing, hence WT is the headline metric.

Reading the results

FCFS — First Come, First Served (non-preemptive; ready queue = FIFO) Gantt: P1 0–7 | P2 7–11 | P3 11–12 | P4 12–16 · avg WT = 4.75, avg TAT = 8.75 Simple & fair by arrival — but the long P1 up front makes everyone queue behind it: the convoy effect (short/I/O-bound processes trail a CPU hog; device utilization collapses). SJF — Shortest Job First (non-preemptive; pick smallest next burst among the ready) Gantt: P1 0–7 | P3 7–8 | P2 8–12 | P4 12–16 · avg WT = 4.00 Provably optimal average waiting time among non-preemptive schedules — moving a short job before a long one reduces the short job's wait more than it grows the long one's. Catch: the next burst length must be predicted — exponential average: τₙ₊₁ = α·tₙ + (1−α)·τₙ. SRTF — Shortest Remaining Time First (preemptive SJF: a new arrival with smaller remaining time preempts) Gantt: P1 0–2 | P2 2–4 | P3 4–5 | P2 5–7 | P4 7–11 | P1 11–16 · avg WT = 3.00 — best of all five here. Watch the simulator: P2's arrival at t=2 preempts P1 (4 < 5 remaining); P3 preempts P2 at t=4. Cost: more context switches; long jobs can starve. Priority — non-preemptive, lower number = higher Gantt: P1 0–7 | P2 7–11 | P4 11–15 | P3 15–16 · avg WT = 5.50 P3 (lowest priority) waits 11 units — in a busy system it might wait forever: starvation. Cure: aging — gradually raise the priority of long-waiting processes. (SJF is priority scheduling with priority = predicted burst.) Round Robin — quantum q = 2 (FCFS + preemption every q; ready queue circular) Gantt: P1 | P2 | P1 | P3 | P2 | P4 | P1 | P4 | P1 · avg WT = 5.00, avg TAT = 9.00 Nobody waits more than (n−1)q before the next turn → excellent response time: the interactive-systems algorithm. Tuning: q → ∞ degenerates to FCFS; q → 0 drowns in context switches. Rule of thumb: q large vs switch cost, small vs typical burst (∼80% of bursts inside one quantum).
Numericals: (1) WT is NOT "start − arrival" under preemption — always compute WT = TAT − BT; (2) in RR, note your tie convention (new arrival enters the queue before/after the preempted process) and apply it consistently; (3) in priority questions, read whether LOWER number means higher or lower priority — both conventions appear.

PID 12

Thread Scheduling · Summary & Likely Questions

  • On modern systems the OS schedules kernel threads, not processes. For many-to-many/many-to-one models the thread library first maps user threads onto LWPs: PCS — process-contention scope (competition among threads of the same process, priorities set by the programmer); the kernel then schedules kernel threads onto CPUs: SCS — system-contention scope (competition among all threads in the system). One-to-one systems (Linux, Windows) use SCS only.
  • Pthreads exposes the choice: PTHREAD_SCOPE_PROCESS vs PTHREAD_SCOPE_SYSTEM via pthread_attr_setscope().
